# 产品文档

## 1. 产品定位

Game Quality Hub 是面向游戏项目的质量管理中台 Demo，整合线上问题响应与线下版本质量交付。

中台需要提供 AI 聚类与初步分级、人工分诊与跟进、需求和缺陷处理、测试执行与版本质量判断，以及统计报告能力。

## 2. 业务场景

### 2.1 线上反馈处理

示例来源包括 Discord、Reddit、X、Telegram 等社区或聊天渠道；本 Demo 使用明确标识的模拟渠道数据，不接入真实外部账号。

流程：

1. 原始反馈进入反馈池，保留原文、来源和日期。
2. AI 识别相似反馈，形成或更新聚类工单，给出初始优先级、业务线及判断依据。
3. QA 通过看板查看趋势、热门和高风险聚类，以及工单明细。
4. 业务负责人确认或调整分级、归属与处理结论。
5. 确认缺陷时创建或关联 RD Bug；功能诉求转为 Feature；信息不足、已知问题或非缺陷保留对应结论。
6. 持续跟踪处理、验收和发布，发布后观察同类反馈。

新增相似反馈持续汇入已有聚类并触发重新评估。聚类不等于根因已确认，允许人工拆分和调整。原始聚类工单在转 Bug / Feature 后继续保留，下游处理项可以有多个。

### 2.2 紧急响应

实际影响、影响范围与增长、跨渠道传播和舆情变化共同参与评估。热门问题和高风险低频问题都需要可见。

问题影响扩大时可升级优先级并进入紧急响应，由人工确认或调整。Demo 不自动执行生产级告警、通知或响应时限管理。

紧急处理允许先止损或恢复服务，再完成根因修复。服务恢复与彻底修复分别跟踪，不要求所有事件都先修改代码再恢复。

### 2.3 版本质量交付

流程：

1. 建立版本，明确版本范围和验收要求。
2. 各开发支线开展自动化及人工测试，并进行准入检查。
3. 本次版本范围内达到准入条件的分支合并，形成候选构建。
4. 对候选构建执行核心功能回归、重要新功能集成测试和适用的稳定性验证。
5. 失败项进入缺陷处理，修复后重新执行相关测试。
6. 汇总版本质量报告，形成发布建议和人工发布决定。
7. 发布后验证，并与线上反馈关联观察。

AI 可辅助分析改动、建议测试范围、生成或编排任务、分析失败和汇总风险；测试结论来自实际执行、明确预期和运行证据。

### 2.4 线上与线下闭环

线上问题经确认后关联项目 Bug / Feature、目标版本与验证任务。已解决问题可沉淀为回归用例，纳入后续版本验证。

## 3. 模块范围

### 3.1 Issue Center

- 反馈池：渠道反馈、手工单条、每行一条的批量粘贴和固定模板 Excel 导入；Excel 经解析、校验、预览后只导入有效行。
- Case 附件：单条提报支持最多 5 张 jpg / png / webp；本地预览后只持久化 Mock URL 和附件元数据，不保存 Base64。
- 标签：支持自定义管理、人工打标、AI 建议后人工确认。
- 聚类工单：摘要、原文证据、渠道与时间分布、反馈增长、AI 初判及依据、业务线、负责人、人工结论、关联处理项。
- 看板与搜索：查看趋势、热门、高风险及待处理问题，按项目、渠道、时间、优先级、业务线和状态筛选。
- 跟进：转 Bug / Feature，查看下游处理、验收和发布情况。
- 日报和周报：分别提供报告入口，支持项目与日期选择、原文摘录、关联工单跳转、Markdown 导出。

系统将原始渠道内容（Signal）、结构化反馈（Case）与聚类问题（Issue）分层表达。Case 保留原文、来源、AI 建议、标签和关联关系；Issue 承载正式 Classification、Priority、Owner / Team、Ticket、处理状态、阻塞原因和修复后观察。首页区分受时间筛选影响的流量指标与当前存量指标，并按优先级、异常增长和存在时间排序。

Issue Center 首页以活跃 Issue 为主要工作区，Open Issue 状态分布作为固定窄栏辅助信息。Latest Case 固定只读展示最新 5 条，与 Cases 主表统一为 Case／来源／Tags／Case Status／Linked Issue；使用低饱和品牌色渠道标签帮助识别来源，不重复展示 AI Classification、置信度或分类理由。模拟性质仍保留在数据、测试记录和页面级能力说明中。

Issue Center 按 Overview / Cases / Issues / Reports 分工。自动采集、手工单条与手工批量反馈进入同一 Case Pool；来源渠道与采集方式独立保存。Cases 支持“全部 Case／我的 Case”、组合筛选、Case 详情、Issue 关联与标签确认；主列表不展示 AI Classification，Tags 列在已确认时只展示人工 Tags，待确认时以 `AI · Tag` 弱标识展示建议。Issues 支持统一标签筛选和 Issue Tag 编辑。

Issue Center 的四个页面由侧栏二级导航直接进入，页面内部不再保留重复导航。Case Status 固定为 Pending / Needs Info / Linked / Closed；Case 的 AI 建议固定为 Bug / Feature / Non Issue / Unclear，只作为辅助信息，不作为正式分类。Issue Classification 固定为 Pending / Bug / Feature / Improvement / Non Issue，并与 Issue Status 独立。

Case 是原始反馈证据，Issue 是持续跟踪的问题。单条、批量粘贴与单 App Excel 导入均可在创建 Case 后选择仅保留 Case、全部关联同 App 已有 Issue，或全部建立一个 Pending / P2 / 未分配的新 Issue；多 App Excel 只导入有效 Case。用户主动选择 Tags 时直接记为已确认，否则保留确定性 Demo AI 建议并进入待确认。关联成功后 Case 状态统一变为 Linked；Store 强制 Case 与 Issue 的 App 一致，并从当前真实关联重算 `feedbackIds`、`caseCount`、`firstSeenAt`、`lastSeenAt` 与 `caseCount24h`。

标签库支持搜索、新增、重命名和删除；删除只解除 Case / Issue 标签关联。AI 建议标签与人工确认标签分别保存，未选初始 Tags 时按反馈文本使用确定性规则生成闪退、登录、性能、支付、网络、玩法、社交、账号、安全、UI、数值或文案建议，无命中时保持空建议。Case Detail 默认选中待确认建议，允许删减、增补或确认为空；只有 `confirmedTags` 参与查询和周报统计。周报的 Bug / Feature Case 只根据关联 Issue 的正式 Classification 统计，未关联 Case 的 AI 建议不进入正式分类指标。周报基于 `caseCreatedAt` 实时计算所选周期及等长上一周期，包含指标环比、高频问题趋势、新增热点、核心问题、Issue 闭环、修复效果、跨周遗留、需要推进，以及可编辑的模拟“本周发现／建议改进”；预览后可复制或下载结构一致的 Markdown。

Issue 与 Case 分别使用持久化的 `ISS-xxxx` 和 `CASE-xxxx` 业务 ID，与内部 EntityId 分离。Issue 列表、Issue 详情、Latest Cases 和关联证据使用同一编号；新建对象根据当前最大序号生成下一编号，刷新后不变。

Bug 不再是 Issue Center 内的独立实体，而是 `Classification = Bug` 的 Issue；继续使用 `ISS-xxxx` 编号。Issues 默认进入 Bug 视图，一级切换为 Bug／待判断／Feature／Improvement／全部，Non Issue 仅在全部视图查看。页面统一使用“新建 Issue”入口，提供 App、标题、Summary、Classification、Priority、Owner 和 Tags；选择 Bug 时在同一 Sheet 补齐 Module、Severity、Assignee、复现步骤与截图说明。Issue Detail 的人工分诊可修改 Classification、Priority 与 Owner；转为 Non Issue 时关闭 Issue，非 Bug 转 Bug 时必须补齐 Bug Detail，Bug 转为非 Bug 时清空 Bug Detail。Bug Status 与通用 Issue Status 保持映射，“已关闭”与“不予修复”均为终态并记录解决时间。

Bug 类型 Issue 增加复现步骤、所属模块、Severity、截图说明、Assignee 和 Bug Status；Severity 与 Priority 独立记录。Bug Status 为待分诊、已指派、修复中、待验收、已关闭、不予修复，每次变更写入 Issue History。

Bug 建立支持四种操作：Pending Issue 确认为 Bug；未关联 Case 单条或批量直接转 Bug；已关联 Case 将其现有 Issue 确认为 Bug；QA 直接提 Bug 或通过固定 Excel 模板批量导入。多 Case 仍遵循 N Case → 1 Issue，已关联 Case 不重复创建 Issue。

Issues 的 Bug 视图提供 App、Module、Severity、Priority、Status、Assignee 和 Tags 筛选，高亮未分配，并统计未关闭、待分诊、未分配、今日新增、按模块及按 Severity 分布。Bug 及其他分类列表的 Cases 列统一展示总数、最近 24h 数量和对比上一个 24h 的趋势，Activity 展示基于统一 Demo 时间工具计算的最近反馈和更新相对时间。当日分诊汇总支持复制和下载 Markdown；Overview 补充 Bug 快捷指标和待推进 Bug，周报补充 Bug 分诊指标与专属字段。

| 报告维度 | 日报 | 周报 |
| --- | --- | --- |
| 目的 | 发现当日异常，推动及时处理 | 观察趋势和处理效果 |
| 反馈情况 | 当日新增、渠道分布、较昨日变化 | 本周总量、每日趋势、较上周变化 |
| 重点问题 | 新增高风险、突增聚类、升级事件 | TOP 问题、持续高发、跨周遗留 |
| 处理进展 | 当日分诊、转 Bug / Feature、解决情况 | 本周处理进展、积压和处理耗时 |
| 待办 | 待确认、未接手、紧急处理 | 长期未解决、反复出现、需纳入版本 |

报告支持按标签统计排行。AI 基于统计和工单记录生成摘要，人工可编辑、确认和保存；历史报告保留当时数据快照。

### 3.2 版本管理

版本管理聚合多个游戏，每个游戏包含多个版本。需求与 Bug 可先进入项目待办池，不强制绑定目标版本。

- 需求与 Bug：管理待办、责任人、分诊、流转，以及来源 Case 和版本关联。
- Bug 基础字段：标题、复现步骤、所属模块、严重程度、截图说明、指派人。
- Bug 流转：涵盖待分诊、已指派、修复中、待验收、关闭／不予修复；支持验收失败退回和重新打开，记录每次流转时间。
- 严重程度与处理优先级分别记录；已验收与已发布分别跟踪。
- 分诊统计：按模块、严重程度统计未关闭 Bug，导出当日分诊汇总。
- 版本：管理范围、开发支线、构建、测试进展与阻塞问题。
- 版本 Overview：按游戏和 iOS / Android 平台筛选 Version；Version 展示覆盖平台、范围、提测进度和平台 Build。缺陷与质量报告只在关联 Build 能明确解析平台时进入平台筛选结果。
- 提测检查：模板与检查项分组，按次生成实例；实例明确版本与提测对象；逐项完成或跳过，跳过必须填写原因；展示处理率、关键项跳过和检查状态，导出记录。
- 版本质量报告：汇总测试对象、覆盖与执行情况、验证结果、遗留缺陷、风险和发布建议。
- AI 辅助：建议 Bug 模块与严重程度、相似 Bug 查重；根据版本说明生成检查单草稿。

提测检查按“选择版本与提测对象 → 选择场景与模板 → 填写版本更新说明 → 生成模板快照与模拟 AI 草稿 → 人工确认 → 执行与导出”工作。预置客户端常规版本、客户端 Hotfix、配置／数值更新等场景与模板；模板支持创建、编辑、删除、分组、检查项维护与关键项标记，新模板默认包含“基础检查”和一个空检查项。实例关联 Project 与 Version，并保存提测对象和带关键属性的模板快照；模板后续编辑或删除不改写历史实例。

检查项来源区分模板、AI 建议和人工新增。模拟 AI 以提测场景、模板已有项和版本更新说明为输入，用确定性规则生成包含标题与原因的结构化建议；QA 可编辑后接受或忽略，只有接受的建议进入实例，AI 不自动完成检查项。检查项状态为待处理、完成、跳过；关键项和普通项都可跳过，但必须填写原因。列表主状态为“进行中／已完成”，详情保留“检查中／检查完成，有跳过项／检查完成，无跳过项”；这些状态只表达检查记录，不作为版本质量结论。用户操作使待处理项由 1 变为 0 时，详情先展示最终状态，再约 600ms 自动关闭；打开历史完成实例不自动关闭。页面继续展示“已处理率 =（完成数 + 跳过数）÷ 总项数”和关键项跳过数。实例记录支持包含完整基本信息、统计、关键属性和处理记录的 Markdown 与 CSV 导出。

### 3.3 测试中心

- 用例库：增删改查；字段包括模块、标题、前置条件、测试步骤、预期结果、优先级。
- AI 用例草稿：根据需求描述生成，由人确认后使用。
- 测试活动：确定用例范围、目标构建、平台和执行人员。
- 执行记录：通过、失败、阻塞、未执行，保留备注与执行证据。
- 结果处理：按平台与模块统计，导出本轮测试报告。

通过率必须明确分母，并同时展示执行进度、阻塞和未执行数量。

测试中心按“用例库／测试执行／测试报告”分工。用例明确所属游戏和 Android／iOS 平台，历史执行保存标题、模块、前置条件、步骤、预期、优先级与平台快照；后续编辑或删除用例不改写已有执行。执行最小单位为“用例 × 平台”，通过、失败、阻塞计入已执行，未执行不计入。执行进度 = 已执行数 ÷ 总执行项；通过率 = 通过数 ÷ 已执行数，尚未执行任何项目时显示 `--`。

测试结论使用固定 Demo 规则：存在未执行项时为“测试未完成”；全部执行且存在失败或阻塞时为“存在风险”；全部执行且无失败、阻塞时为“测试通过”。这不是正式发布 Gate。AI 用例生成继续使用确定性本地规则并标记“模拟”，只有人工选中确认的草稿才进入用例库。测试失败不自动创建 Issue，也不新增资源占用逻辑。

### 3.4 设备与资源

- 类型：测试设备、测试账号。
- 基础资料：型号、系统版本、用途标签等适用字段。
- 调度日历：按日期展示当前筛选范围内的可借数量、总量、可用率与可用／预约／占用／离线分段容量；支持设备／账号及其快捷分类切换。选中日期先看状态摘要与资源分组，再进入具体资源列表。
- 预约：记录预约人、用途、开始／结束日期和可选测试活动；同一资源的重叠区间必须拦截。
- 借还：借用人、用途、借出时间、预计归还时间、实际归还时间。
- 查询：提供不跟随顶部筛选的全局搜索，覆盖资源名称、型号、系统版本、平台、标签、借用人和用途；区分当前占用与未来预约，并展示已借用天数和预计归还日期。
- 超期：作为占用状态的异常子集醒目标识，默认按超期天数倒序，支持类型、平台、借用人筛选，以及按当前筛选结果导出 CSV／Markdown 催还清单。
- 冲突：已占用资源不能重复借出；人工借用与自动化任务共享占用状态。
- 历史：借还记录和关联执行历史。
- 个人视角：独立展示当前用户持有的全部资源、预计归还日期和超期天数，不跟随快捷分类筛选。
- 资源信用：仅展示固定示例分数与同时占用额度，不实现动态积分或真实权限限制。

Demo 使用确定性生成器提供 160 台设备与 120 个测试账号；Reset Demo 后恢复完全一致的数据、借用、预约、离线和超期分布。系统按日期管理资源容量、预约与实际占用关系。远程控制、安装构建、小时级预约、审批／候补、账号密码管理和生产级多人实时同步不属于本 Demo 范围。

## 4. 核心关联与数据原则

| 对象 | 关系与规则 |
| --- | --- |
| 原始反馈 | 保留原文和来源，关联聚类工单；反馈量不等于受影响用户数 |
| 聚类工单 | 聚合多条反馈，关联 Bug / Feature；AI 初判与人工结论分开保留 |
| Bug / Feature | 属于项目，可待排期；关联来源 Case 与目标版本 |
| 版本 | 承接交付范围、构建、检查实例、测试结果和质量报告 |
| 用例／检查模板 | 长期复用；修改不应改写历史执行或检查实例 |
| 测试任务／执行记录 | 任务定义测试目标，每次执行或重跑产生独立记录 |
| 设备与资源 | 关联借用人或测试任务，统一占用状态 |

发现版本与目标修复版本分别保留。验收通过不代表已经发布，转 Bug 不代表原始问题已经解决。

## 5. 报告原则

- 保留反馈日报、反馈周报、当日分诊汇总、本轮测试报告、提测检查记录、催还清单和版本质量报告。
- 日报／周报导出 Markdown；测试结果、提测检查和资源清单按页面提供 Markdown 或 CSV 导出。
- 各业务报告在所属模块提供入口，版本质量报告汇总与该版本相关的证据，无须增加一级报表中心。
- 反馈条数与聚类工单数分开统计。
- 版本质量报告绑定具体构建；构建变化后需要补充相应验证并更新结论。
- 系统汇总事实、AI 辅助解释风险、QA 确认测试结论、版本负责人作出发布决定。
- 发布建议区分建议发布、有条件发布、暂缓发布。有条件发布记录风险、接受人和后续处理安排。
- 未执行或缺少证据的测试标记未验证，不推测为通过。

## 6. Demo 范围与演示场景

项目提供拿到代码后可本地运行、视觉统一且核心操作真实联动的 Demo，采用统一的 Starter 页面骨架和 Claude Theme，具体见设计文档。

业务状态使用统一前端 Store 并保存到 LocalStorage，不需要数据库或外部服务。示例数据围绕演示故事组织，支持恢复初始 Demo 状态；重置只作用于本 Demo 自有数据。

AI 使用简单确定性的规则模拟，对新增输入提供响应，保留无法判断及人工覆盖路径。报告数字与事实从业务状态计算，模拟 AI 仅辅助摘要、风险解释和建议。

生产部署、多人协作、权限、多租户、云同步、测试失败转 Issue、失败项重跑比较和真实执行平台不属于本 Demo 范围。

Demo 覆盖四模块中的人工操作、状态流转、模块关联、历史记录、资源借还和报告导出，并保存操作结果。

外部消息、AI 分析、代码合并事件和自动化执行使用明确标注的模拟数据，不表示已完成真实服务接入。

### 场景 A：线上登录失败

集中反馈 → 聚类与初判 → 人工定级 → 转 Bug → 关联版本 → 测试与验收 → 发布记录 → 日报／周报体现进展。

### 场景 B：新版本组队功能

建立版本 → 提测检查 → 支线准入 → 合并后的候选构建 → 测试轮次与设备 → 核心回归及新功能集成验证 → 失败转 Bug → 修复后重跑 → 版本质量报告。
